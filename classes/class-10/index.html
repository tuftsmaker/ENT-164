Device to Cloud

Build a weather station. A DHT22 on your ESP32 reads the room and posts the number to a Vercel app every ten seconds. A page shows the latest reading, adds a five-day forecast, and lets you set a threshold that turns on an LED.

Read the room

Three wires and a pull-up. The DHT22 is slow and a little fussy, so wire it once and carefully.

The wires

  • VCC to 3V3
  • GND to GND
  • DATA to a free GPIO, the one opencode picks
  • 10 kΩ from VCC to DATA

Two things that bite

  • 3.3 V, not 5 V. The ESP32 pins are not 5 V tolerant.
  • Two seconds between reads. Faster gives stale numbers, then errors.

The module

The three-pin module has the resistor built in. The bare four-pin sensor needs it, or the data line floats.

Ask opencode which pin it used. In MicroPython the sensor is sensor = dht.DHT22(Pin(n)), then sensor.measure(), then sensor.temperature() and sensor.humidity(). opencode does not show the board's serial output, so the browser is how you check the numbers.

Serve it

Before the cloud, prove the chain on your own network.

First, register the board. Tufts Wi-Fi expects a sign-in the ESP32 cannot do, so register its MAC address at access.tufts.edu/manual-non-browser-device-registration before you connect. Until it takes effect, wlan.isconnected() stays False.
GET /readings

An endpoint on the board

The ESP32 runs a tiny server. Open http://the-board-address/readings on the same Wi-Fi and the temperature and humidity come back as JSON.

why

It is your console

opencode cannot show you the board's serial output, so the browser is how you check the sensor and the Wi-Fi before anything else.

next

Then swap it

With the number proven, the server is replaced by the POST loop. From here the page is the console.

Upload it

Every ten seconds the board sends one reading to your own app, and gets one number back.

The contract: POST /api/readings with {"station": "medford-01", "temp_c": 21.4, "humidity": 48} answers {"ok": true, "threshold_c": 24}. Agree on this shape before you ask an AI for code.

Behind the route there are two Postgres tables: readings grows by a row every ten seconds, and settings is a single row holding the threshold. The app creates both on its first request, so there is no SQL console and no schema step. The code lives in a GitHub repository imported into Vercel, so every push redeploys the site; you never see the machine.

The database, in one click. Add Neon from the Vercel Marketplace at vercel.com/marketplace/neon, choose Create New Neon Account, and attach it to the project. The free plan is enough.

Show it

Two sources on one page: your room, and the next five days.

From your board

The page calls GET /api/readings/latest every five seconds and draws the newest row with its timestamp.

From the weather API

GET /api/forecast calls Open-Meteo on the server and caches it for half an hour. Five days of high and low.

One big number

Temperature large, humidity and the time underneath, the forecast as five small cards. That is the whole page.

If the forecast fails, the page still shows the room. One source down must not blank the other.

Set a threshold

A number on the page reaches the board, ten seconds later.

Type it

On the page

  • A number field and a save button
  • POST to /api/threshold
  • One row changes

Pick it up

On the board

  • The reply to its upload carries the threshold
  • No second request
  • The board cannot be called, so it asks

Act

The LED

  • One comparison
  • One pin
  • On above the threshold, off below
Demo it: set the threshold below room temperature on your phone. Within ten seconds the LED is on, and you have built the whole loop.

For your final project

This is the smallest complete version of what a connected product needs.

input

A reading worth keeping

One sensor, recorded over time, is more convincing than five that disagree. Pick the number your product depends on.

output

Something the page can change

A threshold, a mode, a color. The web page should be able to act on the build, not only watch it.

honesty

Design for the day it is down

If the API or the network fails, say so and keep working. A fallback is part of the design.
