Intelligent Device

A device that reaches outside itself: it calls a cloud API, puts a model behind a button, and keeps working when the network or the model does not. The Week 11 material — APIs and AI on real hardware.

Not available yet 5 tasks planned Signed off by a TA
This track is not open yet. The tasks below are what it will contain, written down so the shape of it is clear. The videos have not been recorded and the checks have not been built, so nothing here can be submitted or signed off.

Why this track

Week 11 is where the course asks for the hardest thing it covers — a device whose behaviour depends on services it does not control. The class walks through exactly that build (the poetic light): recording that would not save, an SD card that struggled, a firmware switch, a model that ran out of context. Every one of those was a real failure a student would meet, and none of them are covered by "does it compile". This track is where the engineering practice of working with AI gets written down instead of left to luck.

What it will contain

Planned

Call a cloud service and use the answer

(to record) the request, the key, the response, and the shape of a failure

Evidence: the script plus the parsed value shown on the device

Would check: the key is read from config, never written in the script; the request has a timeout and a failure path; the response is parsed rather than printed raw

Planned

Put an AI model behind a button

(to record) the request to the model, and what comes back

Evidence: the script and a demo of the device responding to a prompt

Would check: the call is parameterised rather than hardcoded; the model's reply is handled as text the device can act on; a missing or malformed reply does not hang the device

Planned

Keep working when the call fails

(to record) timeouts, retries, and what the device does while it waits

Evidence: the script plus a note on what the device shows when the service is down

Would check: every network call is bounded by a timeout; the device has a defined state for "waiting", "failed" and "answered"; no infinite retry loop

Planned

Keep the keys out of the code

(to record) where a key lives on a microcontroller, and why not in the script

Evidence: the script and a note on where the key is stored

Would check: no key, token or password literal anywhere in the submitted code; the script reads from a config that is not itself submitted

Planned

Document what you built and what it cost you

(to record) the build conversation, decisions, and what had to be given up

Evidence: the running conversation link, and a written account of the failures

Would check: a person reads it — the process, the dead ends, the trade-offs accepted

Then: Demonstrate the round trip

Show the device working with a TA present: the service responds, the model answers, and the device does something visible about it. Then show what happens when the network is off, because that is half the engineering.

What it needs first

Two honest limits. First, most of this track cannot be checked after the fact: whether the API answered, whether the model was any good, is a demonstration, so a TA has to be there. The checks catch the structure — no hardcoded keys, bounded calls, a defined failure state — and a person judges the rest. Second, it needs somewhere for a device to keep a key that is not the source file. That pattern is worth settling before the videos are recorded, because students will otherwise learn to paste keys into their code.
