Track · planned

Connected Device

A device you control from your phone. The board runs a web server, serves a page, and every control on that page does something real — the Week 6 build, where the interface is the point.

Not available yet 5 tasks planned Signed off by a TA
This track is not open yet. The tasks below are what it will contain, written down so the shape of it is clear. The videos have not been recorded and the checks have not been built, so nothing here can be submitted or signed off.

Why this track

Week 6 is where students meet the idea that a device can *have* an interface — the board runs a web server, the page gets an address, the phone renders it, and a tap round-trips back to the hardware. That is a genuinely new mental model (no separate computer, no app to install), and it is also the thing students most often get "working" without it actually controlling anything. This track makes the interface the deliverable, one piece at a time.

What it will contain

Planned

Get the device on the network

(to record) credentials, the MAC address, the class registration step

Evidence: the script plus the address the device reports

Would check: the code connects and retries rather than assuming success; it prints its address so you can find it; credentials are read from config, not hardcoded

Planned

Serve a page from the device

(to record) the web server that lives on the board

Evidence: the script and a screenshot of the page on a phone

Would check: the handler is a real route rather than a bare response; the page renders in a phone browser with no client library; it still loads after a reboot

Planned

Make a control that changes the hardware

(to record) a button on the page, and what it does to the board

Evidence: the script plus a short clip of the control being used

Would check: the route behind the control changes device state rather than only returning a message; the change is visible on the hardware itself, not just in the browser

Planned

Show the device's state as it changes

(to record) reading a sensor back into the page

Evidence: the script and a screenshot of two different readings

Would check: the value is refreshed rather than fetched once at boot; it is scaled to real units; the page reflects a change you make by hand

Planned

Build the panel you actually want

(to record) putting the pieces together into one interface

Evidence: the script and a screenshot of the finished panel

Would check: every control has a visible effect; the layout survives a phone screen; the page has a defined state while the device is busy

Then: Use it on a phone

Open your device's page on your own phone and operate it with a TA present: press the controls, watch the hardware respond, and show what the page does when the device is unreachable. The interface working is the signoff.

What it needs first

The checks here are structural and stop short of the real question, which is whether the interface is any good: whether a control does something you can see, whether the page is usable on a phone, whether it degrades when the device is asleep. A person judging the demo settles that, so this track leans on the supervised step more than the machine-backed ones. Reaching out to APIs and models from the page is the Intelligent Device track, not this one.
